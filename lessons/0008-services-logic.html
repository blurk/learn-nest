Services and Business Logic: The Heavy Lifting

Lesson 0008 · Practical · structuring logic

The single idea in this lesson: controllers are for routing, services are for thinking. A controller should be "thin" (just delegating), while a service should be "fat" (containing the actual business rules). This separation makes your app testable and maintainable.

1. The "Thin Controller" Pattern

A common mistake for junior developers is putting business logic directly inside the controller. This is called a "Fat Controller."

The Wrong Way (Fat Controller):


@Post()
create(@Body() createCatDto: CreateCatDto) {
  // ❌ BAD: Business logic in the controller
  if (createCatDto.age < 0) {
    throw new BadRequestException('Age cannot be negative');
  }
  const savedCat = this.db.save(createCatDto);
  console.log('Cat saved at ' + new Date());
  return savedCat;
}

Why is this bad? Because if you ever want to create a cat from a different place (like a CLI tool or a Cron job), you have to copy-paste that logic. You cannot reuse it.

2. The "Service Layer" Pattern

The correct way is to move all "thinking" into the Service. The controller becomes a simple coordinator.

The Right Way (Thin Controller):


// cats.controller.ts
@Post()
create(@Body() createCatDto: CreateCatDto) {
  // ✅ GOOD: Just delegating
  return this.catsService.createCat(createCatDto);
}

// cats.service.ts
async createCat(dto: CreateCatDto) {
  // Logic lives here!
  if (dto.age < 0) {
    throw new BadRequestException('Age cannot be negative');
  }
  return this.db.save(dto);
}

Now, your business rule ("Age cannot be negative") is in one place. Any part of your app that uses createCat() will follow the same rule.

3. What actually belongs in a Service?

If you are unsure where to put a piece of code, ask: "Would this logic still be the same if I changed my API from REST to GraphQL or a CLI?"

  • Put it in the Controller if it's about the HTTP layer: reading a header, parsing a query string, choosing which status code to return.
  • Put it in the Service if it's about the Business layer: calculating a price, validating a user's permissions, interacting with a database, sending an email.

4. Service-to-Service Communication

Because services are just providers, they can inject other services. This is how you build complex features from small, reusable pieces.

Imagine an OrdersService. To create an order, it needs to:

  1. Check if the user exists (UsersService).
  2. Check if the item is in stock (InventoryService).
  3. Save the order (OrderRepository).

The OrdersService doesn't do all this work itself; it coordinates other services. This is the "Composition" pattern.

5. The "Service Layer" Mental Model

Think of your app as a restaurant:

  • The Controller is the Waiter. They take the order, check if the customer is at the right table, and deliver the food. They don't cook.
  • The Service is the Chef. They know the recipe, how to use the oven, and how to plate the food. They don't talk to the customer.
  • The Repository/DB is the Pantry. This is where the raw ingredients are kept. The chef goes here to get what they need.

If the waiter starts cooking, the restaurant becomes a mess. If the chef starts taking orders, the kitchen stops working. Keep them separate.
