What a Module Is and What Its Four Properties Are For

Lesson 0003 · Theory · No code yet

The single idea in this lesson: a module is a boundary. It draws a circle around a piece of your application, and decides which other pieces are allowed to see inside. The four properties of @Module() are how you draw and police that circle.

This lesson is the load-bearing piece for the whole course. Once the four properties are intuitive, every later Nest pattern snaps into place. Take your time.

1. The problem modules solve

You have a working Nest application. You wrote a controller, a service, and registered them. So far so good.

Now imagine the application grows: a `UsersController`, a `UsersService`, an `OrdersController`, an `OrdersService`, an `AuthService`, a `MailerService`, a `LoggerService`, a `ConfigService`. Suddenly everything needs everything. The `OrdersService` calls `UsersService`, which calls `MailerService`, which calls `LoggerService`, which calls `ConfigService`. Everything is coupled to everything.

This is the same problem from lesson 0001 — but a level up. The framework gave you structure at the file level. Modules give you structure at the feature level. Without them, you would just have a flat pile of fifty classes with no boundaries.

A module says: "these things belong together, and the rest of the app does not need to know how they work — only what they offer."

2. The mental model: rooms with doors

Picture a building. Each feature is a room. Inside the room, the people (controllers, providers) talk freely to each other — no restrictions. They share whatever's in the room.

The room has doors. Some doors are open (the room exports something). Some doors are open and lead to other rooms the room needs (the room imports something). Closed doors mean: "this is private, do not look in here."

That is a module. Inside: free communication. Outside: only what is explicitly offered.

Three consequences:

  • Encapsulation by default. Just being in the same app is not enough. Two classes in different modules cannot see each other unless something makes it possible.
  • The module is the unit of reuse. If you want to lift `UsersModule` into a different project, you lift the whole room — it is self-contained.
  • The application is a tree of rooms. The root module (your `AppModule`) sits at the top and imports the feature rooms underneath.

3. The four properties

When you write @Module({ ... }), you pass an object with up to four keys. Each one has one job. Memorize the jobs, not the syntax.

controllers — the people at the front desk

Controllers are how HTTP traffic enters the room. You list them here so Nest knows to instantiate them and register their routes.

If a class is not listed in controllers, Nest will not register its routes — even if it has @Controller() on it. The decorator is not enough; the registration is what counts.

Job: declare which classes receive HTTP requests in this module.

providers — the people who do work

Providers are the services, repositories, factories, helpers — anything that holds logic or data access. You list them here so Nest's container can create them and inject them wherever they are needed.

Like controllers: if a class is not listed in providers, the container will not manage it. It becomes invisible to dependency injection.

Job: declare which classes are managed by the IoC container for this module.

imports — the doors this room opens to other rooms

If a class in this module needs a provider that lives in another module, you must list that other module in imports. Importing a module means: "I want to use providers from that module."

But — and this is the strict part — you can only use providers from an imported module if that module has put them in its exports array. Imports open the door. Exports are what is on the table behind it.

Job: declare which other modules this module depends on.

exports — what this room offers to other rooms

If you want providers from this module to be usable by other modules, you must list them in exports. Otherwise they stay private to this module, even if another module imports you.

This is the public API of the module. Anything not in `exports` is internal.

Job: declare which providers from this module are available to other modules.

4. How the four properties relate

Picture it as a single rule: to use a provider from module A in module B, two things must be true at the same time:

  1. B lists A in B's imports.
  2. A lists the provider in A's exports.

Forget either, and the wiring fails. This strictness is intentional: it forces you to be explicit about who depends on whom. The result is a dependency graph you can read.

5. The default: encapsulation

Modules encapsulate by default. Nothing is shared unless you say so.

This is the opposite of how some other frameworks work, where anything can reach anything. In Nest, if you have not written an import or an export, you have not opened the door.

The reason is the same as every other design decision in Nest: trade a little up-front boilerplate for a lot of long-term clarity. Six months from now, when you ask "where does this class come from?", the answer is one step away: read the imports.

6. The root module

Every Nest application has exactly one root module. This is the class passed to NestFactory.create() in `main.ts`. Conventionally it is called `AppModule`.

The root module is special only in one way: Nest starts walking the tree from here. Beyond that, it is just another module with the same four properties. Most often, its only job is to import all the feature modules and let them wire up together.

Job: be the entry point that lists every feature module the application uses.

7. Two properties you might also see

You will sometimes encounter two more, mostly in special cases. Hold these in mind; we will return to them later.

  • global (set via the @Global() decorator on the class, not the object): a module marked global does not need to be imported to be used. Its providers are available everywhere. Use sparingly.
  • Dynamic modules: a module that exports a forRoot() or register() method so it can be configured at import time. ConfigModule.forRoot() is the canonical example — you tell it which .env file to load when you import it.

You can ignore both for now. The four properties above are 95% of what you will use for the rest of this course.

8. The mental model, condensed

Hold this single image:

  • Module = a room.
  • Controllers in the module = the front desk, where requests come in.
  • Providers in the module = the people who do the work.
  • Imports = doors leading to other rooms this room needs.
  • Exports = what is on the table behind this room's door, for other rooms to use.

Read any Nest application's module tree. Each module is a room. The imports/exports tell you which rooms talk to which other rooms, and what they share when they do.

Retrieval practice

Cover the answers. Answer out loud or in writing. Do not scroll back.

  1. What problem do modules solve that just having a flat list of classes does not?
  2. Name the four properties of @Module({ ... }) and state the job of each in one short sentence.
  3. Two modules, A and B. A provider from A is needed inside B. What two things must be true at the same time?
  4. True or false: if a class has the @Controller() decorator but is not listed in any module's controllers array, Nest will still register its routes. Explain.
  5. What is the root module's job, beyond being "where the application starts"?
Click to reveal the model answers
  1. Modules give you structure at the feature level: they let you group related code, encapsulate what is private, and declare explicitly what is shared. Without them, everything would be coupled to everything.
    • controllers — declare which classes receive HTTP requests in this module.
    • providers — declare which classes are managed by the IoC container for this module.
    • imports — declare which other modules this module depends on.
    • exports — declare which providers from this module are available to other modules.
  3. B must list A in B's imports, and A must list the provider in A's exports. Either alone is not enough.
  4. False. The decorator is metadata; the registration in controllers is what makes Nest actually instantiate the class and register its routes. Without the registration, the decorator's note is never read.
