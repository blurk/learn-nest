The Safety Net: Unit Testing with Jest

Lesson 0020 · Practical · Proving your code works

The single idea in this lesson: Manual testing (clicking buttons in Swagger) is slow and prone to error. Unit Testing allows you to write small scripts that test a single "unit" of logic (usually one method in a service) in isolation. If you change a line of code and the test turns red, you've caught a bug before it ever reached a user.

1. The Testing Pyramid

Professional apps use three types of tests:

  • Unit Tests: Tests one function/method. Very fast. No DB, no Network. (The base of the pyramid).
  • Integration Tests: Tests how two parts work together (e.g., Service + DB). Slower.
  • E2E (End-to-End) Tests: Tests the whole flow from HTTP Request to DB and back. Slowest. (The top of the pyramid).

2. Meet Jest

NestJS comes with Jest pre-installed. Jest is the industry standard for JavaScript/TypeScript testing. It provides the tools to "assert" that a result is what we expect.

Common Jest Commands: - expect(value).toBe(expected): Simple equality. - expect(value).toEqual(expected): Deep equality for objects/arrays. - expect(fn).rejects.toThrow(): Checks if a promise fails.

3. The Magic of Mocking

We want to test the UsersService, but the service depends on the UsersRepository. We don't want our unit test to actually touch the SQLite database, because that makes the test slow and "unstable" (what if the DB file is missing?).

The solution is a Mock. A mock is a "fake" version of the repository that we control. We tell the mock: "When the service calls findById, don't go to the DB—just return this fake user object I created."

4. Step 1: Creating the Test File

Nest usually creates a .spec.ts file for every service. Create /src/users/users.service.spec.ts:


import { Test, TestingModule } from '@nestjs/testing';
import { UsersService } from './users.service';
import { UsersRepository } from './users.repository';
import { NotFoundException } from '@nestjs/common';

describe('UsersService', () => {
  let service: UsersService;
  let repository: UsersRepository;

  beforeEach(async () => {
    // 1. Create a "Mock" of the repository
    const mockRepository = {
      create: jest.fn(),
      findById: jest.fn(),
      findAll: jest.fn(),
      findByEmail: jest.fn(),
    };

    const module: TestingModule = await Test.createTestingModule({
      providers: [
        UsersService,
        {
          provide: UsersRepository,
          useValue: mockRepository, // Inject the fake instead of the real one
        },
      ],
    }).compile();

    service = module.get<UsersService>(UsersService);
    repository = module.get<UsersRepository>(UsersRepository);
  });

  it('should be defined', () => {
    expect(service).toBeDefined();
  });

  it('should throw a NotFoundException if user is not found', async () => {
    // ARRANGE: Tell the mock to return null
    jest.spyOn(repository, 'findById').mockResolvedValue(null);

    // ACT & ASSERT: Check if the service throws the correct error
    await expect(service.getUserById('123')).rejects.toThrow(NotFoundException);
  });

  it('should return a user if found', async () => {
    const mockUser = { id: '123', username: 'testuser', email: 'test@test.com' };
    // ARRANGE: Tell the mock to return our fake user
    jest.spyOn(repository, 'findById').mockResolvedValue(mockUser as any);

    // ACT
    const result = await service.getUserById('123');

    // ASSERT
    expect(result).toEqual(mockUser);
  });
});

5. Step 2: Running the Tests

You don't use `npm run start:dev` for tests. You use the test runner. Run this in your terminal:

npm run test

If you want to run tests in "Watch Mode" (re-run when you save), use:

npm run test:watch

How to verify your work

  1. Run the command: Run npm run test.
  2. Check the output: You should see a green checkmark next to your tests. If a test fails, Jest will tell you exactly what the Expected value was vs the Actual value.
  3. Try a "Breaking Change": Go to `users.service.ts` and change the `NotFoundException` to a `BadRequestException`. Run the test again. It should turn red! This proves your test is actually guarding your logic.
Reflect: Notice that we tested the UsersService without ever touching the database or starting the HTTP server. This is why unit tests are so powerful—they are instant, isolated, and reliable.
