The First Code: Scaffold and Bootstrapping

Lesson 0005 · Practical · First look at files

The single idea in this lesson: we are moving from the "What" to the "Where". We will scaffold a project and map every file to the theoretical concepts (Modules, Providers, Decorators) we've discussed. No logic yet — just orientation.

1. Scaffolding the project

Nest provides a Command Line Interface (CLI) that handles the "Convention over Configuration" part of the mission. Instead of creating folders by hand, the CLI generates a standardized structure that every Nest developer recognizes.

To create a new project, you run:

npm i -g @nestjs/cli
nest new my-nest-app

This creates a directory with a set of "starter" files. These files are the minimum viable structure required to bootstrap the IoC container and start the server.

2. The "Big Four" Starter Files

When you open src/, you will see these four core files. Let's map them to the theory.

main.ts — The Ignition Switch

This is the entry point of your application. Its only job is to tell the IoC Container to start.

Inside, you will see NestFactory.create(AppModule). This is the moment the "Librarian" starts walking the shelves, reading decorators, and wiring the graph. If main.ts doesn't run, nothing else exists.

app.module.ts — The Root Room

Remember the "Root Module"? This is it. It is the top-level room that imports all other feature rooms. It is the starting point for the dependency graph.

You will see the @Module() decorator here with its properties (imports, controllers, providers). This is where you register your "Front Desk" and "Workers".

app.controller.ts — The Front Desk

This is your first Controller. It has the @Controller() decorator. Its job is simple: receive an HTTP request and return a response. It doesn't do "work"; it delegates work to a provider.

app.service.ts — The Worker

This is your first Provider. It has the @Injectable() decorator. This is where the actual business logic lives. The controller asks the service for data, and the service provides it.

3. The Theory-to-File Map

Let's connect everything we've learned so far to these files:

Concept Where it lives in the files
Decorators as Metadata The @Module() in app.module, @Controller() in app.controller, etc.
IoC Container / Bootstrapping The NestFactory.create() call in main.ts.
Module Boundaries The @Module({ ... }) object in app.module.ts.
Dependency Injection The constructor(private appService: AppService) in app.controller.ts.
Singleton Default The fact that AppService is listed once in providers and shared by any controller.

4. The Bootstrapping Sequence

When you run npm run start, this is the exact order of events:

  1. Node.js executes main.ts.
  2. NestFactory is called with AppModule.
  3. The Container scans AppModule. It sees AppController and AppService in the decorators.
  4. The Container notices AppController depends on AppService.
  5. The Container instantiates AppService (the provider).
  6. The Container instantiates AppController and injects the AppService instance into its constructor.
  7. The Server starts listening on port 3000.

Retrieval practice

Cover the answers. Do not scroll back.

  1. Which file is responsible for "igniting" the IoC container?
  2. In the starter project, where do you register a new controller so that Nest knows to register its routes?
  3. If you want to see where the "Root Module" is defined, which file do you open?
  4. Looking at app.controller.ts, how does the controller actually get the AppService instance? (What is the mechanism called?)
  5. True or False: The @Injectable() decorator on app.service.ts is what actually creates the service instance. Explain.
Click to reveal the model answers
  1. main.ts (specifically the NestFactory.create() call).
  2. In the controllers array of the @Module() decorator (usually in app.module.ts).
  3. app.module.ts.
  4. Dependency Injection. It is declared in the constructor, and the IoC container injects it at runtime.
  5. False. The decorator is just a "sticker" (metadata). The IoC Container is what actually creates the instance after reading that metadata.
