Handling Data: POST, Body, and DTOs

Lesson 0007 · Practical · Writing data

The single idea in this lesson: receiving data from a user is dangerous. You should never trust a request body. We use DTOs (Data Transfer Objects) to define the contract and Validation Pipes to enforce it before it ever touches our business logic.

1. The POST Request and @Body()

While GET requests put data in the URL, POST requests put data in the Request Body. This is usually a JSON object. To access this in Nest, we use the @Body() decorator.


@Post()
create(@Body() createCatDto: any) {
  return this.catsService.create(createCatDto);
}

The @Body() decorator tells Nest: "Take the JSON body from the incoming request and map it to this variable."

2. The Danger of any

In the example above, we used any. This is a disaster waiting to happen. Why?

  • No Autocomplete: Your IDE doesn't know what's inside the body.
  • No Safety: If the user sends { "age": "ten" } instead of a number, your service might crash.
  • Over-posting: A malicious user could send { "isAdmin": true }. If you pass the whole body to your database, they just gave themselves admin rights.

3. The Solution: DTOs (Data Transfer Objects)

A DTO is a simple class that defines exactly what a request should look like. It is a contract between the client and the server.


// create-cat.dto.ts
export class CreateCatDto {
  name: string;
  age: number;
  breed: string;
}

By replacing any with CreateCatDto, you tell Nest (and your fellow developers) exactly what data is expected for this operation.

4. Enforcing the Contract: Validation Pipes

A DTO is just a TypeScript type. But remember: TypeScript types are erased at runtime. A user can still send a string where you expected a number.

To stop this, Nest uses Validation Pipes. A pipe is a piece of code that "intercepts" the request before it hits the controller. It checks the data against the DTO.

We use the class-validator library to add rules to the DTO:


import { IsString, IsInt, IsNotEmpty } from 'class-validator';

export class CreateCatDto {
  @IsString()
  @IsNotEmpty()
  name: string;

  @IsInt()
  age: number;

  @IsString()
  breed: string;
}

Now, if a user sends { "age": "ten" }, the Validation Pipe sees that @IsInt() is violated and immediately throws a 400 Bad Request. Your controller method is never even called. Your logic stays clean because it only ever receives valid data.

5. The POST Lifecycle (Mental Model)

Trace the journey of a POST request with validation:

  1. Client sends POST with JSON body.
  2. Express/Fastify receives raw JSON.
  3. Validation Pipe reads the CreateCatDto and checks the decorators (@IsInt, etc.).
  4. Decision Point:
    • Invalid? → Throw **400 Bad Request** → Client gets error.
    • Valid? → Move to controller.
  5. Controller receives the validated object via @Body().
  6. Service saves the data.
  7. Response is sent back with a **201 Created** status.
