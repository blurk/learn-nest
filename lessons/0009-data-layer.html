The Data Layer: Repositories and Entities

Lesson 0009 · Theory · Database mental model

The single idea in this lesson: Your services should not care *how* data is saved (SQL, MongoDB, or a text file). They should talk to a Repository, which acts as a mediator between the business logic and the database.

1. The "Leak" Problem

Imagine your service writes raw SQL queries:


// ❌ BAD: Database logic leaking into the service
async findUser(id: string) {
  return this.db.query(`SELECT * FROM users WHERE id = '${id}'`);
}

This is dangerous for three reasons:

  • Fragility: If you change a column name in the database, you have to find and replace every single SQL string across your entire app.
  • Untestability: To test this service, you must have a real database running. You cannot easily swap the DB for a "fake" one during tests.
  • Security: Writing raw strings like the example above opens you up to SQL Injection attacks.

2. The Repository Pattern

The **Repository Pattern** creates a layer of abstraction. Instead of the service talking to the database, it talks to a Repository. The Repository is a provider that specializes in "data access."

The service says: "Give me the user with this ID." The repository handles the SQL, the connection, and the raw data fetching.

The Right Way (Using a Repository):


// users.service.ts
async findUser(id: string) {
  // ✅ GOOD: The service doesn't know HOW it's found, just that it IS found.
  return this.usersRepository.findById(id);
}

3. What is an Entity?

If the Repository is the "manager" of the data, the **Entity** is the "shape" of the data. An Entity is a class that maps directly to a database table.

If you have a `users` table in PostgreSQL, you create a `User` entity in NestJS. Every property in the class corresponds to a column in the table.


// user.entity.ts
export class User {
  id: number;
  username: string;
  email: string;
  passwordHash: string;
}

The Repository's job is to take raw rows from the database and turn them into **Entity objects** that your services can use.

4. The Data Flow (Complete Picture)

Now we can connect everything from Lesson 0001 to now. Here is the full journey of a "Find User" request:

  1. Client hits GET /users/123.
  2. Controller captures the ID and calls usersService.findOne(id).
  3. Service applies business rules (e.g., "is this user active?") and calls usersRepository.findById(id).
  4. Repository runs the SQL, gets a row from the DB, and maps it into a User Entity object.
  5. Service receives the Entity, maybe maps it to a UserResponseDto.
  6. Controller returns the DTO to the client.

5. The "Swap" (Again!)

Because the service only depends on the Repository's interface, you can swap the database without the service ever knowing.

You could start your project with a MemoryUserRepository (just a JavaScript array) for fast prototyping. When you're ready for production, you swap it for a PostgresUserRepository. Your `UsersService` doesn't change a single line of code because both repositories provide the same findById() method.

Click to reveal the model answers
  1. To decouple the business logic (Service) from the data access logic (Database), preventing the service from being tied to a specific DB implementation.
  2. An Entity represents the data as it exists in the database (internal). A DTO represents the data as it is sent over the network (external).
  3. 1. Fragility (changing DB columns breaks code everywhere) and 2. Security (SQL Injection).
  4. The Repository.
  5. You can replace the real Repository (which needs a DB) with a "Mock Repository" (a fake one in memory), allowing you to test the service in isolation.
