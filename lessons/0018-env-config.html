Professionalism: Environment Variables & Config

Lesson 0018 · Practical · Securing your secrets

The single idea in this lesson: Never hardcode secrets (API keys, DB passwords, JWT secrets) in your source code. If you push your code to GitHub, those secrets are public. We use a .env file to keep secrets on your local machine and the ConfigService to access them in NestJS.

1. The Danger of Hardcoding

Imagine your code looks like this:


JwtModule.register({
  secret: 'MY_SUPER_SECRET_KEY_123!', // ❌ DANGEROUS
})

If you commit this to a public repository, a bot will find that key in seconds. A hacker can then use that key to forge a JWT and log into your app as any user, including the Admin. This is one of the most common ways real companies get hacked.

2. Step 1: Installing the Config Package

NestJS provides a dedicated module to handle environment variables. Run this in your terminal:

npm i @nestjs/config

3. Step 2: Creating the .env file

Create a file named .env in the absolute root of your project (next to package.json, NOT inside /src).

Add your secrets there in KEY=VALUE format:


JWT_SECRET=a_very_long_random_string_that_only_i_know
DB_DATABASE=db.sqlite
PORT=3000

Crucial Step: Create a .gitignore file in your root (if you don't have one) and add .env to it. This tells Git: "Do not ever upload this file to the cloud."

4. Step 3: Activating ConfigModule

We need to tell Nest to load the .env file when the app starts. Edit /src/app.module.ts:


import { Module } from '@nestjs/common';
import { ConfigModule } from '@nestjs/config'; // 1. Import this
import { TypeOrmModule } from '@nestjs/typeorm';
import { UsersModule } from './users/users.module';
import { User } from './users/user.entity';

@Module({
  imports: [
    ConfigModule.forRoot({ 
      isGlobal: true, // 2. Make config available everywhere without re-importing
    }),
    TypeOrmModule.forRoot({
      type: 'sqlite',
      database: process.env.DB_DATABASE, // 3. Use the env variable!
      entities: [User],
      synchronize: true,
    }),
    UsersModule,
  ],
})
export class AppModule {}

5. Step 4: Using ConfigService in your Code

Now, instead of hardcoding the secret in your `AuthModule` or `Guard`, you use the ConfigService to fetch it at runtime.

Edit /src/auth/auth.module.ts (Dynamic Config):


import { Module } from '@nestjs/common';
import { JwtModule } from '@nestjs/jwt';
import { ConfigModule, ConfigService } from '@nestjs/config';
// ... other imports

@Module({
  imports: [
    UsersModule,
    PassportModule,
    JwtModule.registerAsync({
      imports: [ConfigModule],
      inject: [ConfigService],
      useFactory: async (configService: ConfigService) => ({
        secret: configService.get<string>('JWT_SECRET'), // Fetch from .env
        signOptions: { expiresIn: '1h' },
      }),
    }),
  ],
  providers: [AuthService],
  controllers: [AuthController],
})
export class AuthModule {}

And finally, update your /src/auth/jwt-auth.guard.ts to be professional:


import { ConfigService } from '@nestjs/config';

@Injectable()
export class JwtAuthGuard implements CanActivate {
  constructor(
    private readonly jwtService: JwtService,
    private readonly configService: ConfigService // Inject ConfigService
  ) {}

  async canActivate(context: ExecutionContext): Promise<boolean> {
    // ... token extraction logic ...
    try {
      const payload = await this.jwtService.verifyAsync(token, {
        secret: this.configService.get<string>('JWT_SECRET'), // Clean and secure!
      });
      // ...
    } catch {
      throw new UnauthorizedException();
    }
  }
}

How to verify your work

  1. Test the Secret: Change the JWT_SECRET in your .env file and restart the server. Your previous tokens should now be invalid (you'll get 401), because the "key" changed.
  2. Test the DB: Change DB_DATABASE=test.sqlite in your .env. Restart. You should see a new test.sqlite file created, and your previous users will be gone because you are now using a different database file.
Reflect: You have just implemented the "Industry Standard" for configuration. Your code is now 100% portable. You can give your code to a teammate, and they just create their own .env file with their own passwords, and the app works perfectly without touching a single line of TypeScript.
