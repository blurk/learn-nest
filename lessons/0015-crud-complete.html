Completing the CRUD: Update & Delete

Lesson 0015 · Implementation · Full lifecycle management

The single idea in this lesson: Managing data isn't just about adding and finding. To finish a CRUD API, we need to handle Updates and Deletions. We will learn the professional way to do this: using Partial Updates (PATCH) and Safe Deletions.

1. Update: PUT vs PATCH

In REST APIs, there are two ways to update data. Juniors often use them interchangeably, but they are very different:

  • PUT (Full Replace): The client sends the entire object. If you forget a field, that field becomes null in the DB. (Rarely used in modern APIs).
  • PATCH (Partial Update): The client sends only the fields they want to change. If they only send the email, the username stays exactly as it was. (Industry Standard).

2. Step 1: The Update DTO

We can't reuse `CreateUserDto` because for an update, all fields should be optional. We don't want to force the user to send their email if they only want to change their username.

Create /src/users/dto/update-user.dto.ts:


import { IsEmail, IsOptional, IsString, MinLength } from 'class-validator';

export class UpdateUserDto {
  @IsOptional() // The key to PATCH: the field can be missing
  @IsString()
  @MinLength(3)
  username?: string; // The '?' means it is optional in TS

  @IsOptional()
  @IsEmail()
  email?: string;
}

3. Step 2: The Repository Logic

TypeORM makes partial updates easy. The .save() method is smart: if the object has an ID, it updates; if not, it inserts.

Add these methods to /src/users/users.repository.ts:


async update(id: string, data: Partial<User>): Promise<User> {
  // 1. Merge the existing user with the new data
  await this.ormRepo.update(id, data); 
  // 2. Return the updated version
  return this.findById(id)!; 
}

async delete(id: string): Promise<void> {
  await this.ormRepo.delete(id);
}

4. Step 3: The Service Logic

The service handles the business rule: "You cannot update a user that doesn't exist."

Add these methods to /src/users/users.service.ts:


async updateUser(id: string, updateUserDto: UpdateUserDto): Promise<User> {
  const user = await this.getUserById(id); // Reuse existing method for 404 check
  return this.usersRepo.update(id, updateUserDto);
}

async deleteUser(id: string): Promise<void> {
  const user = await this.getUserById(id); // 404 check
  await this.usersRepo.delete(id);
}

5. Step 4: The Controller Gateway

Now we add the @Patch and @Delete endpoints.

Edit /src/users/users.controller.ts:


import { UpdateUserDto } from './dto/update-user.dto';
import { Delete } from '@nestjs/common';

// ... inside the class

  @Patch(':id')
  async update(@Param('id') id: string, @Body() updateUserDto: UpdateUserDto) {
    return this.usersService.updateUser(id, updateUserDto);
  }

  @Delete(':id')
  async remove(@Param('id') id: string) {
    return this.usersService.deleteUser(id);
  }

How to verify your work

  1. Partial Update: Send a PATCH request to /users/{id} with { "username": "new_name" }.
    Verify that the username changed but the email stayed the same.
  2. Delete: Send a DELETE request to /users/{id}.
    Try to GET the user again; you should get a 404 Not Found.
  3. Safe Deletion: Try to DELETE a user that doesn't exist. You should get a 404 because the service checks existence first.
Pro Tip: Soft Deletes: In real companies, we almost never actually delete data (Hard Delete). We use a Soft Delete. We add a deletedAt column to the Entity. When a user "deletes" their account, we just set the date. This allows us to restore data if the user changes their mind or if there is a legal requirement to keep logs.
